# Mini-Brain Toolkit: Mini-Brain Dream Cycle

> V43, 2026-11-12.

Follow these instructions when the user asks the mini-brain to dream and improve itself — the periodic reflection pass that keeps the brain true and small (principle 10).

**Important:** Read `CLAUDE.md` first for file conventions — those govern all edits made during this cycle.

**This brain's project is the toolkit, and its subject is the mini-brain pattern.** So two phases go beyond a product brain's: Phase 2b checks that the toolkit's definition, procedures and templates still agree and that this brain still obeys them, and Phase 3 widens follow-on research to the memory-systems field and the pattern's scientific grounding. The product is the `mini-brain-toolkit` clone beside this repo, read at its `main` branch (`git -C <clone> show main:<path>`, listed by `git -C <clone> ls-tree -r --name-only main`), never whatever branch it has checked out. **This cycle never edits the product**, which takes changes only by pull request: every problem it finds there goes on the needs-human-decision list, with the file, the text and the fix it suggests.

**Guiding principle:** When in doubt, flag for the user rather than auto-correcting. This cycle detects drift and corrects factual staleness. Strategy and framing changes require human judgment. Version control provides rollback safety, so be thorough about detecting problems — but conservative about changing analytical conclusions. **Exception — Phase 3 stance:** the follow-on-research phase is *adversarial by mandate*. Being aggressive about hunting disconfirming evidence and conservative about auto-applying thesis changes are not in tension — do both.

**Unattended.** The cycle runs with nobody present and never waits on an answer. Every call it would otherwise put to the user goes into the cycle log's needs-human-decision list, where the user acts on it later.

**Confidence discipline.** As you draw each conclusion — *before* writing the edit — state a confidence from 1–100. It is a proxy for how many unknowns remain, not a grade. A score below ~70 is a signal to search harder or to flag rather than edit, and obligates you to name the specific unknowns capping it (an unverifiable claim, an inconclusive agent, a thin search). Never round up to look finished. In Phase 3 the score is additionally bounded by that phase's disconfirmation gate. Carry the final scores into the Phase 6 self-evaluation.

**Context management:** Phase 1 has a bounded footprint (file listings, greps) and is handled directly. File reads are delegated by size: hand a read to an Explore agent only when the read as a whole, all its files together, exceeds roughly 500 lines — below that, read directly. This covers Phase 2's code searches, Phase 2b's cross-doc read, Phase 4's LOG slice and Phase 5's drift read. An agent handed a read only locates and summarizes: what it reports are candidates, each with its text, and every judgment on them stays in the active context. Phase 3 is research-heavy, but the `MBT_COMPARABLES.md` and `MBT_BIOLOGY.md` registries bound it: spawn web-search agents (general-purpose with web search; Explore is file-only and won't reach the web) only where §3a/§3b call for one — **not one agent per thread.** A routine cycle spends at most ~10 sub-agents in total; needing more is itself an issue to flag in the Phase 6 report, not a license to keep spawning. Do the synthesis (feature-level cut, positioning, verdicts) in the active context over registry data, not in sub-agents. Retrieval/change-check agents don't need high reasoning effort — brief them narrowly and prefer a cheaper/faster model where the harness allows. The active context briefs agents, synthesizes, makes editorial judgments, and makes all edits.

**Error recovery:** None. If a file is unexpectedly missing, a tool or agent fails to run, or any step produces an outcome these instructions don't cover — stop the cycle and record the cause in the cycle log. Do not retry, work around, or silently skip. A stopped cycle means the instructions need updating, not that the executor should improvise. A failure a step names its own fallback for — no product clone in Phase 2b, a fetch that can't answer in §3a — is that step's work, not an error: take the fallback, and stop only if the fallback fails too. An interruption the session survives, such as a usage limit, is not such an outcome either: the run continues from where it stopped when the session resumes, and its cycle log entry says so. Weak evidence is not such an outcome: an inconclusive agent result or a claim that can't be verified falls under confidence discipline — it is flagged and scored, never folded in as fact, and the cycle continues.

**Before you begin — orient against the last cycle.** Read the last entry in `MBT_DREAM_LOG.md` (grep the final `---`). Carry forward: (a) what the last cycle flagged as *needs human decision* — resolved, still open, or now actionable; (b) what it said it would change about these instructions; (c) which phases found nothing last time — if nothing relevant has changed since, calibrate effort there instead of re-deriving from scratch; (d) the disconfirmation searches the last Phase 3 already ran, so this run attacks the thesis from a *different* angle rather than repeating a spent search. This makes the dream log an input, not only an output, and is what lets a cycle notice it is re-treading. First run (empty log): note it and proceed.

## Phase 1: Structural integrity

Mechanical checks over this repo's top-level files and `working/`. Run all first; fix any failures before the content phases.

1. **Read index → disk.** Every file in the `CLAUDE.md` read index exists on disk.
2. **Disk → read index.** Every top-level `.md` file (excluding `CLAUDE.md`, `AGENTS.md`, `README.md`, `CONTRIBUTING.md`, and this file) appears in the read index. Flag orphans.
3. **Version headers.** Every top-level file except the version-exempt ones `CLAUDE.md` declares carries a well-formed `> V<N>, YYYY-MM-DD.` line — version and date only. Flag any that smuggled a change note into the header.
4. **Cross-references.** Grep all top-level `.md` files except the logs, which are append-only history, for references to other mini-brain filenames. Every reference must resolve to an existing top-level file, a product file `CLAUDE.md` names, or a script in `tests/` — not an `archive/` copy, not a deleted file. A name given as an example (an invented brain's `ORCHARD_SCOPE.md`), an external file's name (`GEMINI.md`) or a `<LOBESPACE>_*` placeholder refers to no file here and is not checked. Within the docs covered by `CLAUDE.md`'s declared-exemptions table, also hold each mention of another of this brain's knowledge files to that table and to the cross-reference form: a permitted direction only, cited by name, not section number. Naming a file every brain has, a product file, or a test script is not such a mention. A stray section number in an otherwise-permitted reference is a mechanical fix; a forbidden-direction reference usually means content bled across a boundary — flag it for the user rather than just deleting the pointer.
5. **Namespace prefix.** Every top-level `.md` except the files `CLAUDE.md` exempts from naming, and every `working/` doc, carries the `MBT` lobespace. Build `<EXEMPT>` by joining with `|` the basenames without `.md` of the files `CLAUDE.md` exempts from naming; it is a runtime value, not a creation placeholder. `find . working -maxdepth 1 -name '*.md' 2>/dev/null | grep -vE '/(<EXEMPT>)\.md$' | grep -v '/MBT_'` should print nothing — it tolerates a missing or empty `working/` and anchors the lobespace to the start of the filename. Flag any hit.
6. **Working/archive filename leakage.** Grep all top-level `.md` files except the logs for filename mentions, then flag any that **name an explicit `working/…` or `archive/…` path, or resolve to a file that exists in `working/` or `archive/`** — no top-level doc may cite a transient working/archived doc directly. A path given as a pattern or an example (`working/MBT_<WORK>_LOG.md`, an invented brain's `working/ORCHARD_PRESS_YIELD_PLAN.md`), a product file, or an external or other brain's name the comparative docs cite (`AGENTS.md`, `CONVENTIONS.md`, `GEMINI.md`, `log.md`) names no file here and is not a hit. For each real hit: if the file still exists in `working/` or `archive/`, read it, extract the relevant substance, and replace the reference inline with that content; if it no longer exists there, flag for the user — don't guess at the content.
7. **Toolkit release.** If a toolkit clone sits at `~/.claude/skills/mini-brain-toolkit`, `~/.agents/skills/mini-brain-toolkit` or `~/mini-brain-toolkit`, compare the release it has checked out (`git -C <clone> describe --tags --exact-match`) with the newest release tag its remote publishes (`git -C <clone> ls-remote --tags --refs origin`, newest by version order). Change nothing in the clone. When the remote has a newer release, add a needs-human-decision item: update the toolkit with the install line in the newest release's README, then run its `check` on this brain, which brings the brain's procedures up to date. With no clone, a clone not on a release tag, or no answer from the remote, skip this check and say so in the cycle log.

Fix any failures. Report what was found and fixed.

## Phase 2: Scope accuracy

`MBT_SCOPE.md` makes factual claims about the world: the alternatives it assesses, the systems the problem holder works within, and its evidence. These go stale when the world changes without a document update. This phase verifies the claims about systems whose code is in reach; the rest wait for a check with the user present, or for the registry refresh in §3a.

**Extract claims** from SCOPE about any system it describes whose code is in reach, an alternative included but never the project's own code, which SCOPE does not describe — architectural facts (trust boundaries, message flow), **absence claims** ("no control does X" — the most fragile, they break silently when a capability is added, so prioritize them), and control/behavior descriptions. Also list every passage that merely restates what the code plainly shows, and every identifier, setting and count a system's own code is the source of, to flag rather than verify.

**Verify** by spawning read-only subagents with specific claim lists grouped by section. Brief each with the exact claim text and the identifiers it contains; agents search by name, not location, since code moves and gets renamed. Ask each whether the claim is still true. If SCOPE carries an Open Questions section, or `MBT_APPROACH.md` states decisions as open, include those questions in the briefs — for each, report anything that now answers or narrows it; these are flagged with the evidence, never resolved in either document (that's the user's judgment). Check code against its main/current release branch, not feature branches.

**Update.** Stale claims: correct to current state, preserving the document's analytical framing. A claim that changed only because this project shipped is status: flag it for removal, never correct it into SCOPE. Invalidated absence claims: don't just flip "no X" to "X exists" — describe what was added and the gap that remains. Passages that merely restate the code, and identifiers, settings and counts the code is the source of: flag as removal candidates rather than correcting them. Confirmed-accurate claims: note them as verified in the Phase 6 report. Claims this phase does not reach (about evidence, or an alternative or other system whose code is out of reach) are listed in the report as unverified, never a reason to stop.

**Do not** add new goals, scope categories, or boundaries (that's scoping work), delete analytical content because a fact it rests on changed (correct the fact, then check the analysis still follows), or rewrite conclusions — flag for the user if a factual change undermines one. A change bearing on a premise the problem statement states is flagged, never edited, since premises are the problem holder's to settle.

## Phase 2b: Product consistency

The toolkit's code is its definition, procedures and templates, and this brain is the first brain they run on. This phase checks both, reading the product at `main`. With no clone beside this repo, skip the phase and say so in the cycle log. All checks are internal (no web); the cross-doc read covers `MBT_PATTERN.md`, `MBT_LOBES.md`, `MBT_CREATE_BRAIN.md`, `MBT_CHECK_BRAIN.md`, a listing of `templates/` (and `templates/work/`), and the full text of `templates/LOBES_CLAUDE.md` and the maintenance templates, since the multi-lobe-layer check compares rule statements, which a filename listing cannot supply. It also covers this brain's own `CLAUDE.md`, `MBT_SESSION_CLOSEOUT.md` and this file, with `templates/CLAUDE.md`.

**(a) Teaching-artifact consistency.** `MBT_PATTERN.md` and `MBT_LOBES.md` are the spec — the base pattern and its multi-lobe layer; `MBT_CREATE_BRAIN.md` builds it, `MBT_CHECK_BRAIN.md` scores it, `templates/` supplies it. These five must agree. This bears on the open templates-and-reference-sync decision in `MBT_APPROACH.md`. Check:

- **Principles.** `MBT_PATTERN.md`'s principles list is authoritative. `MBT_CHECK_BRAIN.md`'s scorecard must have exactly those principles, same count and meaning, same numbering.
- **File set.** `MBT_PATTERN.md`'s stage tables ↔ `MBT_CREATE_BRAIN.md`'s create-table and stage-3 file list ↔ actual files in `templates/`. Every file named in one appears in the others, and no referenced template is missing. Take each file in the listing of `templates/` and `templates/work/` by name and find the document that names it: a template no document names is orphaned.
- **Multi-lobe layer.** `MBT_LOBES.md` ↔ `templates/LOBES_CLAUDE.md`: the naming grammar, lobespace-ownership and naming rules, placement and log-routing rules, and the per-doctype exemption table must state the same convention in both — the template is the layer's shipped copy and drifts independently. The multi-lobe passages in `MBT_CREATE_BRAIN.md`, `MBT_CHECK_BRAIN.md`, and the maintenance templates must enact that same convention.
- **Lifecycle.** `MBT_PATTERN.md`'s lifecycle section and the procedure/template docs describe the same rituals (session → work item → maintenance).
- **Own maintenance docs.** This brain's `CLAUDE.md` conventions, `MBT_SESSION_CLOSEOUT.md` and this file differ from `templates/CLAUDE.md`, `templates/SESSION_CLOSEOUT.md` and `templates/DREAM_CYCLE.md` where this brain needs them to. Compare each pair for a fix one side holds that would serve any brain and the other lacks. Flag each one: porting it changes a template or this brain's conventions, which is the user's call.

**(b) Self-check.** This brain must still obey the pattern at content-stage-or-better health. Apply `MBT_CHECK_BRAIN.md`'s logic to this brain — do not re-implement it, run it, with the product clone as the install. CHECK is written as a conversation with the user; this unattended run puts each question CHECK would ask on the needs-human-decision list and reads the documents as they stand meanwhile. Expect all ten principles present. Its factual-drift check skips `MBT_SCOPE.md`'s claims about alternatives and evidence, which Phase 2 and §3a cover. The design check is what confirms `MBT_SCOPE.md` and `MBT_APPROACH.md` are still orthogonal; its test is the user's to settle, so this run takes it as already settled in the documents — the premises `MBT_SCOPE.md`'s problem statement states with what makes them binding, and the second approach `MBT_APPROACH.md` names. Run the design check in the active context, never through an agent. A premise stated without what makes it binding, or an APPROACH that names no second approach, goes on the needs-human-decision list, and the design check runs only on what is settled.

**(c) Open-question scrub.** Check each open question in `MBT_SCOPE.md` and each open decision in `MBT_APPROACH.md` against the artifacts (a) read; anything that now answers or narrows one is flagged with the evidence.

**Update.** A divergence in a product file goes on the needs-human-decision list as a proposed pull request, never edited here. A mechanical divergence in this brain's own files (a stale count, a renamed file) is fixed directly, bumping each touched file; a divergence that changes what a principle means, or the pattern's structure, is flagged.

## Phase 3: Follow-on research — adversarial

The dream's outward-looking pass — the brain staying curious about what it doesn't know. `MBT_APPROACH.md` and `MBT_FINDINGS.md` depend on specifics that change independently of the product, above all the harnesses the toolkit installs into: their skill directories, invocation, instruction files and session variables. Check those for **external drift** — versions, renamed or removed features, breaking changes — with web search. Factual corrections (versions, dates): update in place. A change affecting a choice the toolkit made: flag for the user.

This brain's subject is the pattern, so follow-on research also widens to (3a) the competitive/research landscape and (3b) the pattern's grounding in how minds actually work. The **data** lands in the registries — `MBT_COMPARABLES.md` (3a) and `MBT_BIOLOGY.md` (3b), whose content is explicitly uncommitted, so refreshing state and dates there is in-bounds editing; the **conclusions** land in `MBT_RESEARCH.md`. Thesis-level consequences (the product's principles, the `MBT_APPROACH.md` positioning and its bet) are **flagged**, never auto-applied.

**Nap gate.** If every living entry's `verified` date in `MBT_COMPARABLES.md` and every field's `reviewed` date in `MBT_BIOLOGY.md` is fresher than ~30 days, and every Phase 3 flag the last cycle left open waits only on the user's decision, skip §3a and §3b and say so in the report — the registry dates *are* the "is anything stale?" check. A user-requested full re-baseline overrides the gate.

**No web access.** With no web search or fetch available, skip the change-checks and hunts below and the external-drift check above, leave every `verified` and `reviewed` date as it is, and report Phase 3 as not run for that reason, then continue to Phase 4.

**Stance — attack the thesis, don't defend it.** The load-bearing claims — *shrink/forgets-by-design*, the *negative-space rule* (define the brain by what the code can't say), *LLM-as-primary-reader*, *human-curated not machine-managed* — are hypotheses to be attacked with fresh evidence every run. **A cycle that surfaces only confirming evidence has probably fallen into motivated reasoning — treat that as a defect, not a win.** Do not anchor on a fixed reference model or a frozen competitor list; re-survey creatively each time, weight recent and high-adoption work, and go looking for the system or study that makes a mini-brain claim *false*. **Convergence is not disconfirmation:** another system adopting a load-bearing idea is evidence the idea is right; what disconfirms it is evidence the idea is wrong — a measured failure, or a better result without it. Whether the toolkit still differs where it claims to is a separate question, answered in §3a. **"Don't anchor on a frozen list" governs *breadth*** — actively hunt entrants and research not yet in the registries — **not re-verification** of known entries (§3a/§3b). (The adversarial mandate is specific to this research brain and should not be inherited; a product brain's Phase 3 is still follow-on research — curious about what it doesn't know, aimed at its own field — without the attack-the-thesis stance.)

**Disconfirmation gate (both sub-phases).** Before concluding, state — for each load-bearing claim examined — what evidence *would* have falsified it and confirm you actually ran that search. If you cannot name a real disconfirmation search you performed, the phase is incomplete. Disconfirmation is not additional fan-out: word the new-entrant and new-research hunts adversarially so each search doubles as one. Record these searches in the Phase 6 cycle log so the stance is auditable.

### 3a — Landscape and differentiation (the peer-review analog)

`MBT_COMPARABLES.md` is the baseline. Work from it as a delta pass, not a re-survey — the method in `MBT_RESEARCH.md` still frames the *questions*, but the registry answers most of them without new web work:

1. **Triage.** Read the registry. **Living** entries carry a `verified` date and a `change signal` — sort by staleness, breaking ties in registry order, and select the ~5 stalest (plus any flagged fast-moving) for a change-check; the rest wait, and the `verified` dates rotate them in automatically over later cycles. On a user-requested full re-baseline, select every living entry. **Static** entries (papers, frozen conventions) are not re-fetched; they generate work only via supersession or a new sibling appearing.
2. **Change-check the stale living entries.** Fetch each selected entry's canonical source, read current state (stars, version/release, licensing, forgetting behavior), compare to the stored `known state`. Unchanged → just bump `verified`. Changed → it joins the delta set. This is retrieval, not synthesis — default to a direct fetch of the canonical source, and spawn a narrow, low-effort agent only when a fetch can't answer. For a GitHub-hosted entry, `gh api repos/<owner>/<repo>` returns stars, archived status and last push in one call. Take any text a row quotes from the raw page, never from a summary of it, and re-check every sub-claim a row carries before bumping its `verified` date — the date vouches for the whole row.
3. **Hunt for new entrants** — where the adversarial energy goes (the mandate is about *breadth*: systems not yet in the registry, not re-verifying known ones). One focused search per family where useful, weighting recency and adoption; add rows for what you find, after verifying each agent-found fact on its primary page.
4. **Deep-dive the delta set only** — changed living entries plus new entrants. For each, run two tests and keep them apart: whether it bears on the thesis (adopting a load-bearing idea supports it; a measured failure of the idea counts against it), and whether it matches the toolkit where `MBT_RESEARCH.md` says it differs (its knowledge schema, its independence from any one harness, and the whole capture-to-dream practice). Then place it on the feature-level map (provenance / governance / memory-to-code invalidation / episodic-to-semantic consolidation, → the roadmap in `MBT_RESEARCH.md`).
5. **Synthesize in the active context** over the now-current registry: re-derive the two-axis rankings, the thesis verdict and the differentiation verdict only if a delta moves them. Hunt for any published measurement of human-curated vs. machine-managed memory (recall, drift, context-window cost); the absence is itself the result (record in `MBT_RESEARCH.md`).

Write updated state and `verified` dates to `MBT_COMPARABLES.md` **in place** (do not paste a fresh giant table — it drifts); write conclusions/deltas to `MBT_RESEARCH.md`. Evidence against the thesis, or a system matching the toolkit where it differs → flag (the `MBT_APPROACH.md` positioning is the user's call, per `MBT_RESEARCH.md`). Convergence on a load-bearing idea → record it as support, saying what it covers and what it leaves out. A delta that falsifies a claim `MBT_SCOPE.md`'s state of the problem makes about an alternative is corrected there when it is a fact, and flagged when it moves where that alternative stops, since the goals answer those gaps.

### 3b — Biological / theory-of-mind grounding

`MBT_BIOLOGY.md` is the baseline — a mechanism-mapping table holding the verdicts, and per-field entries carrying key research, a `reviewed` date, and any candidate mechanisms. A field's foundational science is effectively static (CLS 1995, SHY 2003/2014, Richards & Frankland 2017 don't move month to month), so this is a *new-research* pass, not a re-derivation:

1. **Re-confirm, don't rebuild.** The mechanism mapping and verdicts in `MBT_BIOLOGY.md` are the standing result. Do not re-derive them from scratch. Read them forward and ask, per field, whether anything you already know contradicts the stored verdict.
2. **Hunt new research per field.** For each field in `MBT_BIOLOGY.md`, search for work published since its `reviewed` date that would strengthen, weaken, or add a mechanism — the adversarial move is going after the result that breaks a "load-bearing" verdict or the mechanism the pattern is missing. Focused, low-effort searches; one per field at most, and skip fields where nothing plausibly moved.
3. **Update in place.** Where new research bears on a field, update that field's research + `reviewed` date and, if a verdict changes, the mapping table — all in `MBT_BIOLOGY.md`. A new candidate mechanism goes in `MBT_BIOLOGY.md`'s candidate list with a status.
4. **Flag candidates for the user.** Each candidate is a proposal, not an edit: the user decides whether it graduates to the roadmap (`MBT_RESEARCH.md`) or escalates to the pattern (`MBT_PATTERN.md`, by pull request). **Do not** fold a mechanism into the pattern here.

Bump `MBT_BIOLOGY.md`. Refresh the headline verdict in `MBT_RESEARCH.md` only if the load-bearing/decorative tally changed.

## Phase 4: Findings extraction and reflow

`MBT_LOG.md` accumulates decisions; some belong in `MBT_FINDINGS.md`. Work-item closeouts promote their own findings, but much of this brain's work is logged in `MBT_LOG.md` outside any work item, where nothing has promoted it. Treat extraction as **primary** for those entries and as a backstop for entries recording a work item's closeout: scan the LOG forward from the last cycle for promotable material. Then reflow. Read `MBT_FINDINGS.md` end to end, directly. The LOG slice is every entry dated on or after the last cycle's date (all of them on a first run). Read it directly when it is under the context-management size threshold. Over it, an Explore agent indexes the slice — each entry's title, date, and a one-line summary of its decisions — and the active context picks from the index every entry whose summary shows a decision, discovery, constraint, or abandoned approach, and reads each one in full. From these reads, collect extraction candidates, contradictions/supersessions, internal contradictions, and reflow issues.

**Extraction.** Candidates: implementation decisions where one option won for non-obvious reasons, constraints that would surprise a future maintainer, approaches tried and abandoned. A discovery that reframed the work, or a decision that shaped the approach, belongs in `MBT_SCOPE.md` or `MBT_APPROACH.md`, not `MBT_FINDINGS.md`: flag it for the user rather than extracting it. Grep `MBT_FINDINGS.md` for each candidate's key terms. A **duplicate** is skipped. A **contradiction/supersession** — the candidate makes an existing finding false or reverses a committed direction — is a rewrite in place (bump the version), not a second finding beside the old one. Write in the existing format: **bold statement**, then a reasoning paragraph that stands without the LOG entry it came from.

**Reflow.** Read `MBT_FINDINGS.md` end to end. Its own rule is "assume the current files are ground truth — don't restate what they show," so a finding now made self-evident by the shipped product is a **stale-now-obvious** removal candidate. Also check redundancy/overlap (merge, preserving every distinct reason) and section drift (wrong grouping, split-worthy section, duplicated/empty header from an append). Structural fixes (merges, section repair) — do directly, bump the version. Removing a finding's *substance* or rewriting a conclusion — flag for the user.

## Phase 5: Enforced terms

This phase keeps `MBT_ENFORCED_TERMS.md` internally sound and true to how its terms are used. Two activities, in order.

**Internal integrity (bounded — handle directly).** Check the file against its own stated rules and entry format. Fix format violations directly and bump the version. An entry whose definition can be made to stand alone only by changing what it says is analytical: flag it, do not rewrite the meaning.

**Drift (one pass).** Read every top-level doc of this brain and the product's `MBT_PATTERN.md`, `MBT_LOBES.md`, `MBT_CREATE_BRAIN.md` and `MBT_CHECK_BRAIN.md` — the product's prose is this brain's subject, so its terms bind there too — with one Explore agent or a direct read per the context-management size rule, reporting every use of a listed term outside its entry's sense, every unlisted term used in two senses where taking one for the other would change what a claim asserts, and any consistently-used unlisted term whose everyday sense or near-neighbor would silently change what a claim asserts. A word with several ordinary senses that context settles is not reported. Name in the agent's brief the candidate terms the last cycle flagged. Do not scan the logs or `archive/`: logs are append-only history and are never revised. Judge each result:

- A **listed** term misused or shadowed by a loose synonym is a wording fix — correct it in place to match the entry, bumping that doc's version; in a product file, flag the fix as a proposed pull request instead. A use showing the *entry itself* is wrong or too narrow is analytical — flag it with the evidence rather than silently redefine the term.
- A **listed** entry with no disambiguation is flagged, never deleted: as needing one when this pass found its term misused, and as a retirement candidate when it did not.
- An **unlisted** term that meets `MBT_ENFORCED_TERMS.md`'s rule for adding an entry is proposed — name, one-line sense, and the evidence — for the user to confirm; never add automatically, because judging a term worth enforcing is a human call.

## Phase 6: Report

Present a summary after all phases complete:

- **Structural fixes** (Phase 1): issues and resolutions, or "none".
- **Scope accuracy** (Phase 2): confirmed accurate (grouped by section, not enumerated), unverified (grouped by kind), and corrections made.
- **Product consistency** (Phase 2b): what agreed; each product divergence as a proposed pull request; this brain's own fixes; anything meaning-level flagged.
- **Files updated** (Phases 2–5): each as `file V<old> → V<new> — one-line summary`.
- **Research — external drift and landscape** (Phase 3, §3a): harness changes, thesis status and differentiation status, each with its evidence, landscape deltas, and flags.
- **Research — biology** (3b): mapping/analogy updates (including any metaphor found broken) and candidate mechanisms flagged.
- **New findings extracted** (Phase 4): each bold statement.
- **Findings reflow**: structural changes applied; substance items flagged.
- **Enforced terms** (Phase 5): internal fixes made, drift corrected, entries flagged, and new terms proposed — or "nothing to change" in one line.
- **Needs human decision**: flags from any phase, each with what changed and the implication.

If a phase found nothing, say so in one line — don't pad.

**Needs-human-decision list.** The dream log entry must include a standalone `## Needs human decision` section — a numbered list where each item states the context, what changed, and the specific decision to make. It is the primary output readers act on, and exactly what the next cycle's orientation step reads — each item must be self-contained, understandable without the rest of the entry. An empty list is fine — write "None" and move on.
